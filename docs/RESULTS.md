## Tamper evidence, demonstrated on the rev A store

The rev A store holds 742 manifest entries, 316 of them failing runs.

| Manipulation | `safegate verify` | Detail |
|---|---|---|
| Delete the 316 failing-run entries | exit 1 | 166 problems, first: `seq gap at 4: expected 3` |
| Flip one failing verdict to pass | exit 1 | first: `entry 3 bad signature` |
| Rewrite the chain without failing runs, re-sign with a new key, no trusted key given | exit 0 | a self-consistent forgery passes plain chain checks |
| Same forgery, verified with the pinned key | exit 1 | 426 entries signed by an untrusted key |
| Same forgery, verified against the published anchor | exit 1 | `anchor out/revA/anchor.json: anchored entry seq 741 is missing` |
| Edit the issued report (NON-CONFORMING to CONFORMING) | exit 1 | `report out/tamper/V-and-V-edited.md: report file does not match any technical file recorded for this campaign (edited after issue, or never issued from this store)` |

The third row is why policy `trusted_signers` and anchors exist: chaining and
signatures verified against a key stored in the same place prove nothing against
someone who can write that place. SafeGate 0.3.0 had exactly that weakness.
